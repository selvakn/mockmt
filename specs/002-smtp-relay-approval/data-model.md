# Phase 1 Data Model: SMTP Relay with Human Approval

**Feature**: `002-smtp-relay-approval` | **Date**: 2026-08-06 | **Plan**: [plan.md](./plan.md)

Storage is the existing SQLite database (`DATABASE_URL`, default `./webmail.db`). Tables are created idempotently by `createTables()` in `internal/mockmt/database.go`, following the existing `CREATE TABLE IF NOT EXISTS` style.

## Relationship to the existing schema

The existing `users` and `emails` tables are **not modified**. No column is added, renamed, or dropped, and no existing query changes. Capture-only mode continues to write to `emails` through `saveEmail`; relay mode writes only to the four new tables. See research R9 — this separation is what makes FR-002 and SC-001 structurally true rather than a promise to be careful.

```text
users ──< emails                         (existing, capture-only, untouched)

queued_messages ──< queued_recipients    (new, relay-only)
       │
       ├──< delivery_attempts
       └──< audit_events
```

`queued_messages` has **no `user_id`** and no foreign key to `users`. That absence is the enforcement mechanism for FR-018a: there is no column into which a recipient identity could be recorded, so relaying cannot provision a portal account for an external address.

## `queued_messages`

One row per message accepted in relay mode. One row is one review decision, however many recipients it carries (FR-021a).

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | no | |
| `message_id` | TEXT UNIQUE | no | generated by `generateMessageID()`, as `emails` does |
| `envelope_from` | TEXT | no | original `MAIL FROM`, retained per FR-013c |
| `header_from` | TEXT | yes | original `From` header, retained per FR-013b |
| `subject` | TEXT | no | parsed for display; `""` when absent |
| `raw_message` | BLOB | yes | complete original bytes (FR-008); `NULL` once purged |
| `size_bytes` | INTEGER | no | survives purging, so the metadata stays meaningful |
| `state` | TEXT | no | see state machine below |
| `failure_kind` | TEXT | yes | `confirmed` \| `indeterminate`; non-null only when `state='failed'` (FR-024a) |
| `failure_reason` | TEXT | yes | human-readable (FR-024) |
| `upstream_response` | TEXT | yes | the accepting `250` text (FR-023) |
| `received_at` | DATETIME | no | defaults to `CURRENT_TIMESTAMP` |
| `decided_at` | DATETIME | yes | when it reached a terminal state |
| `decided_by` | TEXT | yes | reviewer email (FR-023, FR-030) |
| `purged_at` | DATETIME | yes | non-null ⇒ content purged (FR-036) |

**Indexes**: `state` (queue filtering, FR-019); `received_at` (ordering); `state, decided_at` (the retention sweep, FR-033).

**Validation rules**

- `state` constrained by `CHECK (state IN ('pending_review','sending','sent','failed','rejected'))`.
- `failure_kind` constrained by `CHECK (failure_kind IS NULL OR failure_kind IN ('confirmed','indeterminate'))`.
- A message with `purged_at IS NOT NULL` must have `raw_message IS NULL`, and must be refused by the send and retry paths (FR-036).
- Rows are only ever inserted when relay mode is enabled.

### State machine

Exactly the five states of FR-027, and exactly its transitions:

```text
                  ┌─────────────────┐
                  │ pending_review  │ ◀── message accepted over SMTP
                  └────────┬────────┘
              Send Now     │     Reject
            ┌──────────────┴──────────────┐
            ▼                             ▼
      ┌───────────┐                 ┌───────────┐
      │  sending  │                 │ rejected  │ (terminal)
      └─────┬─────┘                 └───────────┘
            │                             ▲
   ┌────────┴────────┐                    │
   ▼                 ▼                    │ Abandon (FR-026a)
┌────────┐      ┌──────────┐              │
│  sent  │      │  failed  │──────────────┘
│(term.) │      └────┬─────┘
└────────┘           │ Retry
                     └──▶ sending
```

Permitted transitions, and nothing else:

| From | To | Trigger | Guard |
|---|---|---|---|
| `pending_review` | `sending` | Send Now | conditional claim wins (R6) |
| `pending_review` | `rejected` | Reject | — |
| `sending` | `sent` | final dot acknowledged | — |
| `sending` | `failed` | attempt failed | sets `failure_kind` |
| `failed` | `sending` | Retry | indeterminate requires explicit confirmation (FR-025a); refused if purged |
| `failed` | `rejected` | Abandon | FR-026a |

`sent` and `rejected` are terminal, and every state has a path to one of them — which is what makes every message eventually eligible for retention purging (FR-035).

**Transitions into `sending` are the concurrency-sensitive ones.** They must be performed as a conditional update whose affected-row count decides the winner (research R6), never as a read-then-write.

## `queued_recipients`

One row per **envelope** recipient (FR-015a). This is the delivery list, not the `To`/`Cc` display list.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | no | |
| `message_id` | INTEGER FK → `queued_messages(id)` | no | |
| `address` | TEXT | no | as given in `RCPT TO` |
| `hidden` | BOOLEAN | no | true ⇒ absent from visible headers, i.e. blind-carbon (FR-015a) |
| `delivered` | BOOLEAN | no | default false; true once served (FR-025) |
| `delivered_at` | DATETIME | yes | |
| `upstream_response` | TEXT | yes | per-address `RCPT` result or rejection |

**Indexes**: `message_id`.

**Validation rules**

- At least one row must exist per message; a submission with zero envelope recipients is rejected at SMTP time, never queued (per the spec's edge case).
- `hidden` is computed at ingest by comparing the envelope address against addresses parsed from the `To` and `Cc` headers, case-insensitively and with display names stripped. A comparison that cannot be resolved resolves to `hidden=true` — surfacing more to the reviewer, never less (research R10).
- `delivered=true` is set when the address was accepted at `RCPT TO` **and** the final dot was acknowledged. Standard SMTP gives one acknowledgement for the whole message, so acceptance is decided per address at `RCPT` and confirmed collectively at the dot (research R4).
- A retry must skip rows already marked `delivered` (FR-025).
- `hidden` affects display only. It must never cause the address to be added to the relayed message's headers (FR-015b).

## `delivery_attempts`

One row per try, so retries are individually recorded (FR-025).

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | no | |
| `message_id` | INTEGER FK → `queued_messages(id)` | no | |
| `started_at` | DATETIME | no | |
| `finished_at` | DATETIME | yes | |
| `outcome` | TEXT | yes | `sent` \| `confirmed_failed` \| `indeterminate`; null while in flight |
| `upstream_response` | TEXT | yes | |
| `error` | TEXT | yes | never contains credentials (FR-006, FR-032) |
| `initiated_by` | TEXT | no | reviewer email, or `system` for the startup sweep |

**Indexes**: `message_id`.

**Validation rules**

- `outcome` constrained by `CHECK (outcome IS NULL OR outcome IN ('sent','confirmed_failed','indeterminate'))`.
- Classification follows the boundary in research R5: everything up to and including a write error before the final dot is `confirmed_failed`; a failure awaiting the final-dot reply is `indeterminate`.
- The startup sweep (FR-028) closes any attempt left open by a crash, writing `outcome='indeterminate'` and `initiated_by` unchanged.
- Attempt rows are **never purged**, so the delivery history outlives the content (FR-034).

## `audit_events`

Append-only. Never updated, never deleted, never purged (FR-030, FR-031).

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | no | |
| `message_id` | INTEGER | no | plain integer, deliberately **not** a cascading FK |
| `from_state` | TEXT | yes | null for the initial enqueue |
| `to_state` | TEXT | no | |
| `actor` | TEXT | no | reviewer email, or `system` |
| `occurred_at` | DATETIME | no | defaults to `CURRENT_TIMESTAMP` |
| `detail` | TEXT | yes | e.g. abandonment of an indeterminate message notes the status was unknown (FR-026a) |

**Indexes**: `message_id`; `occurred_at`.

**Validation rules**

- Written in the same transaction as the state change it records, so the two cannot diverge.
- The FK is intentionally omitted so that no future deletion of a message can cascade away its audit trail (FR-031).
- `detail` must never contain credentials or full message bodies (FR-032).

## Derived, not stored

Computed on demand by re-parsing `raw_message`; deliberately not persisted (research R11):

- **Plain-text body, HTML body** — for reviewer display (FR-016).
- **Attachment list** — filename, declared content type, size (FR-016).
- **Attachment content** — streamed per part for preview or download (FR-016a/016b).

Storing these would duplicate bytes the raw message already holds and create a second place for the retention purge to have to reach. When `raw_message IS NULL` the message is purged: the portal says so rather than showing empty content, and offers no retry (FR-036).

---

## Configuration (not persisted)

`Relay Configuration` from the spec is process configuration read at startup, never stored in the database and never exposed through the API (FR-006). Fields and defaults are tabulated in research R13. Credentials live only in memory and in the operator's environment.
